01

What the project does

We benchmark two estimators of the cis-heritability of gene expression — GCTA/REML (individual-level, the field standard) and a SuSiE fine-mapping estimator we built (summary-statistic based) — to determine when fine-mapping yields more reliable cis-h² than GCTA.

Because ground-truth heritability is never known in real data, the compute core is a simulation engine: it draws a realistic local LD structure from 1000 Genomes, simulates expression with a known true h² under many genetic architectures, runs both estimators, and compares their error. Findings are then confirmed on real GTEx expression data. As a method-evaluation project, cost is dominated by sweeping a large architecture grid across thousands of replicate loci to obtain confidence intervals on bias, power, and type-I error.

Homegrown code — and why it was necessary

~6,000 lines across 32 scripts (Python + R + shell). Small in size, but the scientific core: no existing tool performs this end-to-end simulate-and-compare workflow.

Core design constraint we had to enforce ourselves
The LD used to simulate genotypes must be the exact same ordered LD handed to the fine-mapper, or the comparison is uninterpretable. That alignment is baked into our code — a generic pipeline does not provide it.

5c · From 1 to 1,000 simulations — and why 1,000

The engine is a linear loop over independent replicate loci, so wall-time is linear in the number of simulations. Measured ground truth for one full architecture grid (30 models) on one region: 3.65 min (7.3s/model). So 1,000 loci ≈ 61 core-hours at p≈1.5k, or ~165 SU at a representative p≈3k.

Why 1,000 replicates is scientifically necessary
Power, bias and type-I error are means/proportions over replicate loci, so their CIs shrink as 1/√N. Monte-Carlo SE of a proportion ≈ √(p(1−p)/N): N = 100 → ±5%, N = 1,000 → ±1.6%. Resolving whether SuSiE's type-I error is 5% vs. 7%, or a few-percent bias difference across the h² grid, needs ~1,000 replicates — the standard in the fine-mapping / TWAS-simulation literature (twas_sim, SuSiE papers).

07

Efficiency work & filesystem bottlenecks

Already done to minimize I/O and cost

  • All heavy transient I/O on node-local NVMe, not Lustre — thousands of array tasks never overwhelm the parallel-FS metadata server.
  • Aggressive per-model cleanup keeps the transient-file count bounded across a full grid.
  • Cholesky factored once per region and reused for all genotype replicates (O(p³) paid once, not per replicate).
  • Retry-with-reseed on SuSiE non-convergence, so one bad replicate never wastes a node-hour.
  • Append-only single result table per campaign rather than thousands of tiny output files.
  • Runs past the 48-hour wall limit: independent, checkpointable loci — the result table skips already-completed rows, so campaigns split into requeued Slurm-array chunks and survive the wall-clock cap.
Bottleneck 1 — the LD text file is O(p²) and huge
Measured 93 MB → 2.8 GB → 12.3 GB per model as p grows (matching the 2.4 GB temp_ld.ld still in the repo). This single object dominates I/O and must stay on local NVMe.
Bottleneck 2 — redundant LD recomputation (planned fix)
The LD file is currently recomputed for every one of the 30 grid cells of a region, though the region's genotypes — and thus its LD — are identical across cells. Caching LD once per region removes ~29/30 of that I/O: at p=8k it saves ~23s and 2.8 GB of write per cell.
Bottleneck 3 — metadata churn
Each model creates/deletes ~5 small files; at hundreds of concurrent tasks this stresses the filesystem's create/delete rate more than its capacity — another reason it all lives on node-local NVMe.

Independent of NAIRR: this CPU-only simulation/fine-mapping workload is entirely separate from any NAIRR-pilot GPU/LLM usage.
